# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```console
npm test                          # full ava suite
npx ava tests/comments-api.test.js       # one test file
npx ava tests/comments-api.test.js -m 'snapshots*'   # tests matching a title pattern
npm run lint                      # xo (config in package.json, tuned for CommonJS)

node lib/cli.js <file.md>         # register a file (auto-starts the daemon), print URL
node lib/cli.js daemon            # run the daemon in the foreground (logs)
node lib/cli.js status --json     # daemon health + registered files
node lib/cli.js stop              # stop the daemon

node scripts/marker-state.js backup  state.json   # registrations + comments to a file
node scripts/marker-state.js restore state.json   # put them back into a fresh daemon
```

## Restarting the daemon without losing comments

Comments live in the daemon's memory only, so any restart discards them —
including the restart a change to `lib/*.js` requires. **Check
`lib/cli.js status` for unresolved comments before stopping.** If there are
any, carry the state across instead of asking the user to re-type it:

```console
node scripts/marker-state.js backup /tmp/marker-state.json
node lib/cli.js stop
node lib/cli.js <the oldest registered path> --no-browser --json   # restarts the daemon
node scripts/marker-state.js restore /tmp/marker-state.json
```

`restore` re-registers oldest-first so the index ordering is unchanged, then
recreates each thread, its replies and its resolved state, and finally reads
the daemon back and diffs it against the backup. It exits non-zero and leaves
the backup in place if anything failed to come back. Registration ids are
`sha1(realpath)` so URLs survive; `createdAt` and the per-file comment ids do
not, because the API assigns those on create.

Templates and browser assets (`lib/templates/*.html|js|css`) are read from disk per request — edits show up on browser reload without restarting the daemon. Changes to `lib/*.js` (server, registry, api…) require a daemon restart (`stop`, then re-register files). Comments are in-memory and a restart discards them by design — see "Restarting the daemon without losing comments" above before stopping a daemon someone is reviewing on. `lib/vendor/*` is served with an ETag, so replacing a vendored bundle needs a hard reload.

## Architecture

markserv-marker is a fork of markserv v1.18.0 (first commit is the pristine import). One daemon on a fixed port (default 7642) serves every registered file; the CLI is only a thin client.

**Process/flow**: `lib/cli.js` probes `GET /api/health` (the response must have `name: "markserv-marker"`), spawns `lib/daemon.js` detached if nothing answers, then registers via `POST /api/files` and prints the URL. Two CLIs racing to start the daemon is resolved in `startHTTPServer` (lib/server.js): on `EADDRINUSE` the losing daemon probes health and exits 0.

**Request handling** (`lib/server.js`): no router — a connect middleware stack: `{markserv}`-prefixed bundled-asset handler → `/api` (lib/api.js, hand-rolled method+regex table) → `/f` (registered-file handler) → `/` (index page, favicon, 404). Files are served at `/f/<id>/<path>` where `id = sha1(realpath).slice(0,10)`; the file's **parent directory** is the serve root (relative images and sibling links work), guarded against path traversal by `resolveWithin`.

**State** (`lib/registry.js`): a module-level singleton holding registrations and their comments, in memory only. It is an EventEmitter (`register`/`unregister`) so the hot-reload watcher lifecycle can follow it. Comment ids are `<fileId>-cN`; threads are one level deep (a reply to a reply is re-parented to the root).

**Comment anchoring** — three cooperating mechanisms:
- `lib/source-line.js` (markdown-it plugin) stamps rendered blocks with `data-source-line(-end)`. It also fills in the maps markdown-it 10 leaves off a table body's rows, one source line each, so a row is its own anchor instead of the whole `tbody` — which is what lets a comment name the row it is about and the UI show it there. It must come **after** markdown-it-highlightjs, which replaces the fence renderer and drops token attrs, so fences get attributes injected by wrapping the renderer. That injection only reaches a `<pre>` at the very start of the fence output. `lib/mermaid.js` is the one plugin that takes a fence over completely, which is why it comes after source-line and stamps the same attributes itself. A fence plugin has three choices: sit before source-line and emit a bare leading `<pre>`, sit after it and stamp its own attributes, or sit after it and wrap what the captured renderer returns, which is what `lib/diff-fence.js` does and which needs no stamping at all.
- On comment creation, `registry.narrowRange` shrinks the UI-reported block range to the lines the selected text (`quote`) actually touches, and a `snapshot` of those lines is stored. A short quote can occur several times in one block, so the browser also sends `quoteIndex`, the 0-based occurrence it selected counted over the block's rendered text; `narrowRange` and `highlightQuote` both honour it, clamping when source and rendered text disagree on the count. Absent `quoteIndex` means occurrence 0, which is what pre-existing comments get.
- `getThreads` recomputes `currentText`/`changed` per read and **re-anchors**: stored line numbers are frozen at creation, so when the snapshot text no longer sits at them but is found intact elsewhere, the thread reports the lines it occupies now and `changed` stays false. The copy nearest the original anchor wins, ties going to the earlier one. `snapshot.lineStart/lineEnd` keep recording where the comment was written, and threads are sorted on the re-anchored lines because the browser relies on that order for several comments on one block.

**Hot reload** (`startHotReload` in lib/server.js): one `ws` server; watchers are per-registration-root and refcounted. Messages are JSON envelopes `{type:'reload', html}` / `{type:'comments', fileId}`. The browser swaps `#marker-content` innerHTML and dispatches `marker:reload` / `marker:comments` CustomEvents, which `lib/templates/comments.js` listens to — it rebuilds all widgets idempotently (everything it creates is marked `data-marker-ui`) and preserves in-progress drafts in module state.

**Comment UI** (`lib/templates/comments.js`, vanilla JS, no build step): selection → floating Comment button (mousedown, not click, so the selection survives) → posts line range + quote. Quote highlights are re-found by whitespace-normalized text match, so they survive edits and reloads. Neither those nor `mark.marker-pending` may wrap a text node whose parent is a table structure element — the `UNWRAPPABLE` set — because a `<mark>` dropped straight into a `<tr>` is laid out as an anonymous cell and the table gains a column that is not there. The nodes in question are the whitespace between cells, which a selection crossing two rows takes in and which have nothing to show anyway. `placementFor` decides where a widget goes: a comment on a table row rides in a `<tr data-marker-ui>` of its own directly under that row, its single cell spanning the row's columns, and a comment on a list item goes inside that `<li>` — the way GitHub puts a review comment under the line it is about, since the end of a long table is nowhere near the row the comment is about. Both start collapsed, or an open thread would push the rows around it apart, and the host cell has to be styled as `.markdown-body table td.marker-thread-cell` to shed the padding and borders the theme gives a data cell. Every widget riding in a row is also given a pixel width by `pinRowWidgets`, run at the end of `render`, after a comment form is inserted, and on window resize. A cell in an auto-layout table asks for its content's max-content width, and max-content does not wrap: a thread showing its snapshot diff of a table row, or an editor holding source lines, presents the widest source line as the width it wants, the columns are redistributed around it and the table grows a sideways scrollbar it did not have — measured at 1042px of content becoming 1467px for an editor, and a diff running far past the page for a thread. Prose wraps at word boundaries and costs a cell nothing, which is why a bare thread or form never showed this. With a definite width the diff table's `width: 100%` has something to resolve against and wraps inside it. The width is measured with the table's widgets at `display: none`, because in the layout the table is already the width they made it and would only confirm itself, and it is the *cell* that is measured, not the table: the collapsed border sits inside the table's client width, and a widget given all of it pushed the columns out by that border and left the table one pixel to scroll. But the cell spans the grid, which for a table that scrolls sideways is wider than what shows — measured at 1220px in a table showing 918 — so the width is the smaller of the cell and the table's client width less that border. The width toggle in markdown.html dispatches a `resize` for the same reason the window does: the column changed width and every pinned widget and every sticky-header decision was made for the old one. `box-sizing: border-box` on the cell's child keeps the padding inside the pinned width. A host row also takes a slot in the theme's `tr:nth-child(2n)` striping, so every row below an inline comment swapped shade; markserv.css stripes `table:not(.marker-diff-table) > tbody > tr:nth-child(2n of :not([data-marker-ui]))` instead, with the four themes' row colours moved onto variables, and the snapshot diff's own rows excluded since they too sit inside that tbody. The snapshot diff is written as `.markdown-body .marker-diff-table…` for the reason diff-block.css carries its prefix: a lone class loses to `.markdown-body table td`, and the diff came out `display: block; width: max-content` with the theme's padding and zebra rows, its two columns no longer under the two heads above them. Everything else still lands after the whole block: a `<pre>` or another feature's wrapper has nowhere to put it. Each comment carries a `delete` link, and the thread head carries a 🗑 button that takes the whole thread — the head is the only part a collapsed thread shows, which is the state a thread worth deleting is usually in. Both confirm first, and both stop the click from reaching the head, which would otherwise collapse the thread as well. A 204 to that `DELETE` is logged by Chrome as `net::ERR_ABORTED` because `api()` never reads the empty body; the request succeeds. View modes (all/unresolved/mark/plain) persist in localStorage. **A re-render leaves open input alone.** `clearWidgets` keeps a comment form whose draft is still open and the editor panel (`keptAcrossRender`), and `render` skips rebuilding what is already there: rebuilding dropped the caret, an IME composition in progress and, through the `focus()` that followed, the reader's scroll position — on every comments push, which a review produces constantly (measured: the page jumping 428px back to the form). When the content itself is swapped by a hot reload the elements are gone, so the same facts are kept in state instead: `trackFocus` records which of our textareas the reader is in and their caret, and `restoreFocus` at the end of `render` gives the rebuilt textarea focus with `preventScroll` and the caret back. A textarea the reader asked for — Comment, Edit or Reply just clicked — is focused with scrolling, as `focus()` always did: a form opened below the fold with its caret blinking out of sight reads as a form with no caret, and the reader reaches for the mouse. The native selection is cleared before the form opens, not after, since clearing it after focusing is the order that once took the caret with it. The blur a removed textarea gets arrives while it is still in the tree, so whether the reader has really moved on is decided a tick later, when a removed element has been removed. The selection mark is rebuilt the same way, `restorePendingMarks` finding the draft's quote again exactly as a thread's highlight is found (`locateQuote`), which is also what gives an editor its mark back after a form beside it is cancelled. Reply forms live inside their thread's widget and are rebuilt with it, focus restored. A reload also hides the selection bar and drops `pendingSelection`: the block it pointed at went with the old content, and a form inserted after a detached node appears nowhere; re-opened from its draft, a form is anchored by `lineEnd`, where the original placement put it. Posting a comment clears the selection mark, which would otherwise sit on top of the highlight the comment now carries. `render()` ends by dispatching a `marker:rendered` event, which is how features that read the widgets and highlights stay decoupled from it.

**Mermaid blocks** (`lib/mermaid.js` on the server, `lib/templates/mermaid.js` in the browser, bundle vendored at `lib/vendor/mermaid.min.js`): the server only wraps the fence in `<div class="marker-mermaid" data-marker-wrapper>`, leaving the `<pre><code>` inside byte-for-byte the shape every other fence has, so comments work on the mermaid source with no special case. The browser draws the diagram beside it and adds a per-block toggle. Three constraints hold this together. Everything the browser adds is `data-marker-ui`, because `textEntries` in comments.js would otherwise fold diagram labels into the quote-matching corpus and shift `quoteIndex` counting document-wide. The wrapper itself is **not** `data-marker-ui`, or its source would stop being commentable. And `insertionPoint` climbs out of `[data-marker-wrapper]` parents so thread widgets land after the whole block instead of among the diagram controls. `data-mode` is set by the browser only after a render succeeds, so a failed render or a missing bundle leaves the source visible. Per-block mode is keyed by the block's ordinal among the document's mermaid blocks, because hot reload replaces `#marker-content` wholesale. The toggle is `user-select: none` for the reason the diff block's is: a drag past the end of the first source line ends on it, and an endpoint inside `data-marker-ui` is one `blockOf` refuses.

**Code blocks** (`lib/templates/code-block.js` + `code-block.css`, browser-only): every `<pre>` that no other feature owns is wrapped in `<div class="marker-codeblock" data-marker-wrapper>` and given a toggle between scrolling long lines sideways, which is what the theme does, and wrapping them. It follows the mermaid and diff pattern — wrapper not `data-marker-ui` so the code stays commentable, toggle `data-marker-ui` and `user-select: none`, `insertionPoint` climbing out so widgets land after the block, mode per block by ordinal with the last click remembered in localStorage (`markserv-marker-code-lines`) as the default a block resolves to when built — with two differences. The wrapping happens in the browser, on `DOMContentLoaded` and `marker:reload`: nothing about the served HTML changes, so a running daemon needs no restart, and it must run before comments.js renders, which script order and the synchronous wrap guarantee. And the toggle shows only on a block whose lines actually run past its edge, measured as `scrollWidth > clientWidth`, or one already wrapped, which has to be able to go back; a button on every block read as noise. Wrapping is `.markdown-body .marker-codeblock[data-mode="wrap"] pre > code { white-space: pre-wrap; overflow-wrap: anywhere }`, prefixed to beat the theme's `pre > code { white-space: pre }`, and `anywhere` because a hash or URL has no break opportunity of its own — unbroken, it is what made the block scroll. A click dispatches `resize`, since the block's height changed and everything below it moved.

**Diff blocks** (`lib/diff-fence.js` and `renderDiff`/`diffToHTML` in lib/server.js on the server, `lib/templates/diff-block.js` + `diff-block.css` in the browser, word diff shared through `lib/templates/diff-core.js`): a ```diff or ```patch fence is wrapped in `<div class="marker-diffblock" data-marker-wrapper>` and the browser draws a GitHub-style two-column comparison beside the source, toggling per block. It follows the mermaid pattern above, with three differences worth knowing. The plugin **wraps the previous renderer's output instead of replacing it**, so highlight.js still colours the source and source-line's attributes are already on the `<pre>` — a third option beyond the two the source-line note describes, and the reason it must sit after `./source-line`. `.diff` and `.patch` files get a page of their own through the same template, with content built by handing a synthetic fence token to the real fence renderer, so the file path and the fence path cannot drift; the whole file is one block stamped `data-source-line="1"` to its last line, because `registry.narrowRange` reads the real file and a synthetic markdown wrapper would shift every line by one. And the comparison is `data-marker-ui`, so comments are made on the unified source, exactly as with mermaid. Only the view being shown is in the DOM: hiding the comparison with CSS instead left it between the source and the toggle, and a selection dragged past the end of a line — which is where the toggle floats — ran on through it, pulling the other side's text and the line numbers into the quote and landing its endpoint inside `data-marker-ui`, where `blockOf` refuses to offer the Comment button at all. The source cannot be removed the same way, being what comments anchor to, so in split mode it is hidden and made `user-select: none`; the toggle carries the same, or ending a drag on it would take the endpoint into UI. Inside the comparison, a selection that leaves the cell it started in becomes a cell selection and the browser hands over every cell it touches, so dragging down one column copied the other column's text along with it, tab-separated. Each cell and gutter therefore carries `marker-diffblock-old` or `-new`, a `mousedown` listener marks the view `select-old`/`select-new` for the side the drag started on, and CSS makes the other side `user-select: none` — GitHub's trick for the same problem. A drag starting on a file or hunk header locks to the old side, since locking to neither is what the bug looked like. The parser ends hunks by counting the `@@` header's own line counts rather than by pattern, which is what lets `---` inside a hunk body be an ordinary deletion; a block with no header at all is treated as one hunk with no line numbers, since that is what most hand-written fences look like. Combined merge diffs and blocks past `ROW_CAP` rows are left as source with a note saying why. The CSS carries a `.marker-diffblock` prefix throughout because the github-markdown themes style `.markdown-body table td` and would otherwise turn the comparison into a bordered data grid. The block occupies exactly the width a paragraph does and long lines wrap inside their cell: a full-bleed treatment that broke out of the 978px body column was tried and reverted, because a block hanging outside the page frame reads as broken at any window width, and the page already has a width button for a reader who wants the room. Wrapping is also what keeps the two sides row-aligned, a table row sizing to its taller cell. Its colours are translucent overlays, one set for all four themes, the way the snapshot diff in comments.css does it; the unified source keeps highlight.js's own per-theme diff colours. The two palettes therefore differ, which was tried both ways: giving the comparison the `hljs-deletion`/`hljs-addition` classes matches it to the source exactly, and pushing these values onto those classes matches the source to the comparison, but that second one leaves the unified view too faint to read. The toggle's label names **the view being shown**, not what a click does — read as an action it looks like a state, and mistaking the two costs more than the wording saves; the tooltip carries the action.

**Editing the source** (`registry.replaceLines` + `PATCH /api/files/:id/content` on the server, the `editing the source` section of `lib/templates/comments.js` in the browser): a selection offers `✏️ Edit` and then `💬 Comment`, Edit on the left — one joined control, since two floating buttons side by side read as two unrelated things arriving at once — and it opens a textarea holding those lines plus three either side, written back with `Apply`. The selection stays marked while a form or editor is open: focus moving into the textarea takes the browser's own highlight with it, so the range is wrapped in a `mark.marker-pending` of its own — blue, since amber already means a comment lives there — and unwrapped when the reader moves on. It is deliberately not `data-marker-ui`: it wraps real content, and hiding that text from the quote corpus would shift `quoteIndex` for every thread after it. The editor's textarea carries a gutter of the file's own line numbers with the selected ones picked out, an amber band across those lines, and a stronger band on the selected text itself. The text wraps, so a source line can occupy several rows, and all three are placed by one measurement: a hidden twin of the textarea, one child per line, holding the same text at the same width and metrics — the only way to ask a textarea how tall a line came out or where a substring landed. Each number is then given its own line's height, the line band is the heights before the selection summed, and the quote's rectangles come from a `Range` over the twin's copy of each line, one per visual row. The bands live behind the textarea, which works because `.marker-textarea` is transparent, with the textarea lifted above them so the letters stay on top. The quote is located by searching the selected lines for the text the browser reported, clamped by `quoteIndex` the way `narrowRange` clamps it, so editing that text simply stops finding it and the marks go — showing what was selected, not chasing it. A quote covering more than one line is never there verbatim: the text a selection reports is the rendered text, which has lost its markup, joins soft-wrapped source lines with a space and separates blocks and table cells with newlines and tabs the file does not have — measured as `"…first line, second…"` for a paragraph written across two lines, the space standing where the file has a newline, and `"cell\tnext cell\nrow two\tits cell"` for a selection crossing two table rows. What survives is the words and their order, so the fallback walks them forward through the region and marks the run from the first it finds to the last, separators and markup included, which is what the selection covered on the page too. That loose pass runs once, when the panel opens: the source text it resolves to is what the marks track from then on, matched verbatim and re-found nearest to where it was last seen. Loose matching cannot tell an edit from a difference it was built to tolerate — it still finds the words of a phrase the reader has just rewritten, and the run between the first and the last of them looks untouched — which is why the characters it resolved to are the ones being watched. The panel rides in a table row exactly as a comment does, and like every widget in a row it gets a pixel width from `pinRowWidgets` — see the comment-UI note above for why. `closeEditor` sweeps every panel and the row any of them rode in through `removeWidget`, an emptied host row still holding a column-spanning cell; a comment form's Cancel goes through the same. The panel survives a plain re-render, so when its own content has to change — the disk comparison arriving or leaving — `rebuildEditor` drops it first. `resize: vertical` is off: the panel already grows to whatever the text needs, and dragging the handle smaller was the one thing that clipped the text without clipping the numbers beside it. The line badge's pill is padding around a line box exactly as tall as its digits, and the button's emoji is a flex item of its own: given a taller line box the digits sit high in the pill, and sharing an inline box with an emoji's taller fallback metrics pushes the label's letters down, both of which read as a badge misaligned against the label and neither of which centring the boxes can correct. Only the editor wears a line badge: a comment lands on what the reader just selected and is looking at, while the editor opens a window they have not seen yet, so the badge names the lines it was asked about. This is the **only code in the repo that writes to a served document**, and two things make that safe. It locates the range by the text the caller read (`base`) rather than by line number, using the same `findSnapshotLines` that re-anchors comments — so "the write is safe" and "the comments have not moved" are one predicate, and an edit elsewhere in the file cannot misplace it. And it writes through a temp file renamed into place, because `getThreads` and `getContent` read synchronously on every request and would otherwise see a half-written document, which `getThreads` swallows into "nothing changed". A base that has gone gets a 409 carrying the current text; the browser shows it against what the editor opened on, reusing `diffNode`, and offers `Apply my Edit` (which sets `force`) or `Apply other's Edit`, which keeps what the file already holds and closes. The temp file's extension stays out of `fileTypes.watch`, or it would trip the watcher itself; the line endings of the replaced range are preserved, or every snapshot in a CRLF file stops matching verbatim and every thread reports itself edited. No push is sent after a write: the watcher sees it and re-renders 150ms later, and a second push would rebuild every widget twice. Applied writes have no undo of their own: `↶`/`↷` beside the page controls were shipped and taken out as clutter, the file's own history being the place for that, and typing inside the textarea stays the browser's own undo. The editor lives in comments.js rather than an asset of its own because it hangs off the same selection and reuses `blockOf`, `placementFor` and `insertAt`, all private to that closure; `clearWidgets` sweeps `.marker-editor` too, or a plain re-render would leave a second panel behind.

**TOC entries** (`lib/templates/toc.css`): each entry is a flex row, the heading link shrinking with an ellipsis and the unresolved-comment count fixed beside it. Clipping the list item as a whole — `overflow: hidden` on the `li`, which is what it used to be — took the badge away with the overflowing heading, and the badge is the half that says there is something in that section to read. The link needs `min-width: 0` or a flex item refuses to shrink below its text.

**Sticky table headers** (`lib/templates/table-head.js`, rules in markserv.css): a long table's header row pins to the top of the window, but only on tables that can afford it. The github-markdown theme gives every table `overflow: auto` so a wide one scrolls sideways inside the column, and that makes the table its own scroll container — a sticky header inside it pins to a box that scrolls away with the page, so nothing appears to happen. Turning the overflow off is what lets the header pin to the window, and then a table too wide for its column spills out of the page and takes the page's horizontal scrollbar with it (measured: 554px of it). So the browser decides per table, and it has to measure with the overflow still in place: a table reporting no sideways scrolling to do is one that can give it up, and its header pins to the window (`marker-sticky-head`). A table that does need it cannot have a descendant stick to the viewport at all, so its header row is **copied** into a fixed, clipped shell that follows the table's own horizontal scrolling — `.marker-sticky-shell`, shown only while the table straddles the top edge, `pointer-events: none`, and appended to the `<article>` but outside `#marker-content`: outside so its duplicated text is nowhere near the quote corpus, inside the article because every rule that makes a table look like one is written `.markdown-body table…` and on `<body>` the copy came out in the browser's default serif with no background. Capping the height and scrolling inside the table instead was shipped first and replaced: it works, but it makes the page stop scrolling where the table starts. Letting cells break inside a long word (`overflow-wrap: anywhere`) would make those tables fit and was tried on a real spec page: it does work, and it squeezes the columns until identifiers break mid-word, one camel-case field name spread over three lines, so it was dropped. `overflow-wrap: break-word` does nothing here at all — only `anywhere` counts towards the intrinsic width a table is sized from. `apply()` therefore strips the class and drops every shell before measuring any table, or one that already gave up its overflow measures as needing nothing, or a table that already gave up its overflow reports nothing to scroll however wide it has since become. The copy leaves out every `[data-marker-ui]` row the header has picked up, and `sync()` measures only the header's own cells: a widget anchored to a header row rides in a row of its own inside the `thead`, and copying that hands the page a second, fixed, inert copy of a comment form or an editor — carrying the first one's measured highlight rectangles at coordinates that mean nothing where it landed, and staying there after the real one is closed, since nothing rebuilds the shell on close. Counting its cell in would also shift every copied width by one. Re-run on `marker:reload`, on `marker:rendered` since inline widgets sit in table rows, and on resize. The header's bottom border is redrawn as an inset shadow because a collapsed border belongs to the table, not the cell, and stops being painted once the cell is lifted out of the flow.

**Markdown HTML comments** (`lib/templates/md-comments.js` + `md-comments.css`, browser-only — the server passes `<!-- ... -->` through verbatim, pinned in tests/source-line.test.js): each DOM comment node under `#marker-content` gets a `data-marker-ui` span inserted after it, holding the note as a real text node so it can be selected and copied; the `<!--`/`-->` delimiters are CSS pseudo-elements, so a copy picks up the note alone. `data-marker-ui` is what keeps the note out of the quote corpus (`quoteIndex` for existing threads never shifts) and keeps a selection inside it from spawning the Comment button. A selection straddling a note does pull the note's text into the quote, which then matches nothing — the thread still anchors to its lines, just without a highlight. A small toggle at the right end of the strip above the page frame (a `.marker-md-toggle` child of the `<article>`, created only when the document has comments) toggles `marker-md-comments-hidden` on `<body>`; the body class and the article sit outside `#marker-content`, so both survive hot reload. Persistence is localStorage `markserv-marker-md-comments`, absent = shown. `decorate()` rebuilds idempotently on `marker:reload`. The strip itself — `body.marker-doc` top margin, the positioned article, and the file-path display on the left (long paths collapse their middle segments to `…`, hover shows the full path in a tooltip below the bar, click copies it) — is laid out by markserv.css and rendered by an inline script in markdown.html.

## Testing gotchas

- The registry singleton is shared within a test file — tests are `test.serial` and clean up via `registry.reset()` or explicit unregister.
- ws clients in tests must connect to `ws://127.0.0.1:<port>`, not `localhost`: ava runs test files in parallel processes and the same port number can be bound on IPv4 by one file and IPv6 by another.
- `tests/comment-ui.test.js` runs the real `comments.js` inside jsdom with a mocked `fetch`; jsdom lacks `Range.getBoundingClientRect` and `scrollIntoView`, which the UI code guards for — keep those guards.
- `tests/mermaid-ui.test.js` does the same for `lib/templates/mermaid.js`, with a stubbed `window.mermaid` set before the eval. jsdom cannot run the real library, which is why `ensureLib` checks `window.mermaid` before injecting the bundle — keep that seam. What the diagram looks like and whether `display: none` hides anything are not tested there; jsdom has no stylesheets.
- `tests/source-line.test.js` shares one `fixture` whose line numbers every assertion hardcodes. Add a test with its own document rather than editing it.
- Snapshot/diff tests write to their fixture files and must restore them, since later tests assert on content.
- `xo --fix` can be overeager (it once rewrote a string index loop to `String.entries()`, which doesn't exist) — rerun the tests after any autofix.

## Workflow rules (important)

- Do **not** commit, push, or update the installed Claude Code plugin on your own. Make the changes, report, and wait for the user to ask.
- Work happens on a branch, never directly on `main`. Branch off `main` and name it after the version the work belongs to, `vX.Y.Z-dev`. `main` receives the work by merge, and only a release commit is expected to land on it directly.
- A release ships **code, skills and plugin together** and may span any number of commits. The invariant is the end state, not the commit shape: when the release is cut, `package.json` version == `plugins/markserv-marker/.claude-plugin/plugin.json` version == the `vX.Y.Z` git tag, and the tag points at a commit where both files agree. Never leave one of the three bumped alone.
- Cutting a release means: bump both version files, tag `vX.Y.Z`, push with tags, create the GitHub Release for the tag (`gh release create vX.Y.Z`), and update the installed plugin.
- Releases happen only when the user asks. When release-worthy changes have accumulated, ask the user instead of releasing automatically.

## Review workflow skills / plugin

`plugins/markserv-marker/skills/` defines the human-in-the-loop review flow this tool exists for, split into two skills: `open-markdown` serves a file for a human to comment on in the browser; `review-markdown` reads unresolved threads from the API, edits the file, replies as `author: "claude"` (in the session language) and resolves each thread. Use them when asked to have a markdown file reviewed or to process review comments.

Inside this repo they are available as the project skills `/open-markdown` and `/review-markdown` (via `.claude/skills/` symlinks). The repo is also a Claude Code plugin marketplace (`.claude-plugin/marketplace.json` + `plugins/markserv-marker/`): installed as a plugin, they are `/markserv-marker:open-markdown` and `/markserv-marker:review-markdown`.
